smltxt テキスト圧縮形式の調査報告書
調査対象は GilgameshCaw/Caw の master、コミット 97cd13f3a1423f702d411472fdd2b2a2e7bfbd59 にある smltxt/ です。以下は実装の読解と実行で確認した結果です。推測は含めていません。

リポジトリのファイル変更、コミット、ブランチ作成、PR 作成は行っていません。実行には Node.js を使用し、DB・Redis・Prisma・フロントエンドは使用していません。
1. 圧縮後のバイト列の全体の構造
圧縮形式は、UTF-8 の各バイトを、直前の状態に応じたハフマン符号に置き換える方式です。

先頭にマジックナンバー、バージョン番号、フラグ、元の文字数、元のバイト数、符号表は付きません。構造は次のとおりです。
順序	内容	長さ
先頭から	本文の各 UTF-8 バイトに対応する符号を連結したもの	可変長
本文の直後	終端を示す 1	1 ビット
最後	バイト境界まで埋める 0	0〜7 ビット


つまり、全体は 「本文の符号列 → 1 → 必要な個数の 0」 です。末尾には必ず 1 が残るため、正常な出力の最終バイトは 0 になりません。

本文の有効ビット数は末尾から判定します。元の文字数や UTF-8 バイト数は、復号するまで分かりません。入力バイト列全体の長さは、ブロックチェーン上の格納形式など、外側から与える必要があります。

圧縮結果には符号表の識別情報もありません。そのため、読み取り側は書き込み側と同じ統計表を事前に共有する必要があります。

参照箇所は src/SmlTxt.ts、src/BitWriter.ts、src/BitReader.ts です。
2. 圧縮しないで載せる場合があるか
調査した smltxt 自体には、非圧縮で格納する経路はありません。

短い入力や、圧縮すると大きくなる入力でも、同じ符号化と終端処理を行います。例えば「a」は UTF-8 で 1 バイトですが、結果は 2 バイトです。「aa」は 2 バイトから 3 バイトになります。

圧縮済みと非圧縮を見分けるフラグもありません。したがって、このライブラリの形式だけから「これは生の UTF-8 なので、そのまま読む」と判断することはできません。

これは smltxt/ 内の仕様についての確認結果です。ブロックチェーン側の外側の格納形式に別の区別があるかどうかは、本調査の対象外です。
3. 符号化の単位とビットの並び順
符号化の単位
単位は文字でも単語でもなく、UTF-8 の 1 バイトです。対象となる値は 0〜255 の 256 種類です。

ただし、同じバイトでも、その直前の状態によって使用するハフマン木が変わります。状態は、直前 2 バイトをそれぞれ次の 39 種類に分類して表します。
バイトの種類	分類番号
その他	0
英字 a〜z、A〜Z	1〜26。大文字・小文字は同じ番号
半角空白	27
数字 0〜9	28〜37
ASCII の表示可能範囲のうち、英字・数字・空白以外	38


最後の分類には、一般的な句読点のほか、括弧、スラッシュ、アンダースコアなども含まれます。改行、タブ、非 ASCII のバイトなどは「その他」です。

状態番号は、古い方の分類番号の 39 倍に、新しい方の分類番号を足した値です。全部で 39 × 39、すなわち 1,521 状態あります。

各本文の開始時は状態 0 です。開始前の分類が 2 個とも「その他」である場合と同じ扱いになります。バイトを一つ符号化・復号するたびに、そのバイトの分類を状態へ反映します。

重要なのは、分類するのは直前のバイトであり、現在符号化するバイトそのものを分類番号に置き換えるわけではないことです。現在のバイトは 256 種類のまま区別されます。
ビットの並び順
各バイトの 上位ビットから下位ビットへ順番に読み書きします。ハフマン木では、左枝が 0、右枝が 1 です。

符号の途中でバイト境界をまたいでも、区切りは入りません。次の符号も直後から続きます。

参照箇所は src/SmlContext.ts、src/huff.ts、src/BitWriter.ts、src/BitReader.ts です。
4. 符号表・辞書・統計の表
表が表しているもの
単語辞書ではなく、各状態における、次の UTF-8 バイトの出現頻度を量子化した統計表です。
項目	大きさ
状態数	1,521
各状態の対象バイト数	256
各頻度の保存サイズ	1 バイト
統計表本体	389,376 バイト
埋め込み用の src/tableData.ts	519,558 バイト


統計表本体は、状態番号の小さい順に並び、各状態の中では対象バイト値の小さい順に並びます。状態ごとの領域は 256 バイトです。

この表から状態ごとにハフマン木を作り、圧縮用の符号と復号用の木を導きます。表自体の内容や個別の頻度値は、本報告書には転載していません。
学習入力と作成手順
README と生成プログラムから確認できる手順は次のとおりです。
1. 投稿本文を、1 行につき一つの JSON 文字列として用意する。
2. 元データが data/post-stream/ にある場合、配下の JSON ファイルを読み、各行の includes.posts に含まれる投稿の text を取り出して、この形式へまとめる。
3. 投稿集合を学習用と評価用に分ける。
4. 学習用の各本文を UTF-8 化する。各本文の開始時に状態を 0 へ戻す。
5. 各バイトについて、「その直前の状態」と「現在のバイト」の組合せの出現回数を数える。
6. 状態ごとに頻度を量子化し、統計表本体を作る。
7. 統計表本体を Base64 化し、配布用の TypeScript ファイルへ埋め込む。
README には約 646 万件から学習用 600 万件を切り出す例があります。ただし、これは手順例であり、同梱表が実際にその件数・その投稿集合から作られたことを示す記録ではありません。元投稿の収集元も、この生成処理だけでは確定できません。
頻度の量子化と復元
量子化は状態ごとに独立して行われます。

最も多いバイトの頻度が 10 億になるように、各出現回数を比例拡大します。その後、対数尺度で 0〜255 の整数へ丸めます。尺度の下限は 10、上限は 10 億です。ゼロ頻度も保存値 0 になります。

復元では、10 から 10 億までを 255 段階の等しい比率で増加させた尺度を使い、保存値に対応する重みを整数へ丸めます。隣り合う段階の比率は、1 億の 255 乗根です。

そのため、復元した重みは元の出現回数そのものではありません。また、学習時に出現しなかったバイトにも正の重みが割り当てられます。未出現バイト用の特別な逃がし符号は必要ありません。
同じハフマン木を作るための規則
同じ重みからでも、同順位の扱いが違うと符号が変わります。互換性には、次の規則も必要です。
- 最初の葉は対象バイト値の小さい順に並べる。
- 重みの小さい順に、同じ重み同士の順序を維持して並べる。
- 最小の二つを取り出し、先に取り出したものを左、次を右とする。
- 親の重みは二つの重みの合計とする。
- 新しい親は残りの並びの末尾へ追加してから、再び同じ安定した並べ替えを行う。
したがって、新しい親と既存の節点が同じ重みなら、既存の節点が先になります。一般的なハフマン実装を使う場合も、この同順位規則を合わせる必要があります。
作り直せる範囲と報告書だけでの限界
同じ統計表本体があれば、元の投稿集合なしで、同じハフマン木と符号を再構築できます。

一方、同梱表を学習から作り直すには、元と同じ学習入力が必要です。調査対象には元の学習用投稿集合が含まれていません。別の投稿集合で学習し直しても、既存データとの互換性は保証できません。

したがって、本報告書だけで復号手順は実装できますが、任意の既存投稿を復号するには、別途、同じ統計表が必要です。 大きな表を転載しないという条件上、その不足を本報告書の文章だけで補うことはできません。後述の試験例に必要なビット列だけでは、全状態・全バイトの表は復元できません。

参照箇所は src/sizeEncoding.ts、src/huff.ts、src/parseTableData.ts、src/TableBuilder.ts、programs/digestPosts.ts、programs/buildTableData.ts です。
5. 日本語や絵文字など、ASCII 以外の文字の扱い
日本語や絵文字専用の符号化方式はありません。まず UTF-8 に変換し、構成バイトを一つずつ符号化します。
入力	UTF-8 のバイト数	今回の圧縮結果のバイト数
あ	3	2
漢	3	3
👍	4	4


非 ASCII 文字を構成する各バイトは、状態更新時にはすべて「その他」に分類されます。ただし、符号化対象としてはそれぞれ別のバイト値です。

例えば、本文の先頭から日本語だけが続く場合、状態は 0 のままです。日本語の直後に英字が続く場合は、英字を処理するにつれて状態が変わります。

復号ではバイト列を再構成した後、UTF-8 として文字列へ戻します。Unicode の正規化、かなの変換、絵文字の置換などは行いません。結合文字や絵文字の修飾子も、入力の UTF-8 バイト列に従います。

ただし、使用している標準の文字列変換には次の性質があります。
- 不正な UTF-8 は、復号時に置換文字へ変換されます。
- JavaScript 文字列に単独のサロゲートがある場合、UTF-8 化の段階で置換文字になります。
- 復号後の先頭に UTF-8 の BOM がある場合、標準の復号処理はそれを除去します。
後ろ二つについては補足実験でも確認しました。したがって、あらゆる JavaScript 文字列について完全な往復保存を保証する方式ではありません。今回指定された 12 本文は、すべて圧縮後に元の本文へ戻りました。
6. 終わりの判定と最後の余りのビット
最終バイトの下位側から連続する 0 を除き、その直前の 1 も除いた残りが、本文の有効ビット列です。
末尾の部分	意味
最終バイトの下位側に連続する 0	埋め草
その直前の 1	終端を示すビット
それより前	本文の符号列


終端の 1 は本文中にも現れ得ます。先頭から「1 が来たら終わり」と判断するのではなく、入力全体の最終バイトから有効長を確定する点が重要です。

有効ビットが残っている間、現在の状態のハフマン木をたどります。葉に到達したら 1 バイトを出力し、そのバイトで状態を更新して、次の木の根から読みます。有効ビットを使い切った時点で終了します。

ハフマン符号の途中で有効ビットを使い切る入力は、読み取り不足のエラーになります。末尾バイトが 0 の入力も拒否されます。ただし、チェックサムはなく、壊れたデータを必ず検出できるわけではありません。

空文字列を圧縮した結果は 0x80 です。本文の符号はなく、終端の 1 と埋め草の 0 だけになります。実装は長さ 0 の入力バイト列も空文字列へ復号しますが、通常の圧縮処理が空文字列に対して生成する値は 0x80 です。
7. 大文字・小文字、URL、同じ語の繰り返し
大文字・小文字
現在符号化するバイトとしては、大文字と小文字を区別します。一方、次の符号表を選ぶための状態では区別しません。

したがって「test」と「Test」は先頭の符号が違いますが、その後の状態が一致し、残りの「est」の符号は同じになります。大文字を小文字へ変換したり、大文字フラグを付けたりする方式ではありません。
URL
URL 専用の認識、短縮、置換はありません。 コロンやスラッシュも含め、通常の UTF-8 バイト列として処理します。

今回、本文を https://caw.is として圧縮すると、結果は 0xbdffe4d6866c8584 でした。提示された期待値とは一致しません。

提示された期待値を同じライブラリで復号すると、https://tencawffee.com/s/knTDbd になりました。その文字列を再圧縮すると、提示された期待値と完全一致しました。

これは実行で確認した事実です。期待値が https://caw.is からその値へ変化した経緯については、判断していません。
同じ語の繰り返し
単語辞書への登録、前方参照、繰り返し回数の記録はありません。

「test test」の二つ目の「test」が一つ目と異なる符号になるのは、直前の状態が異なるためです。一つ目は本文開始の状態から始まり、二つ目は直前の「t」と空白が作る状態から始まります。

二つ目の語でも「te」まで処理すると、一つ目と同じ状態に到達します。そのため、残りの「st」は同じ符号になります。これは単語の再利用ではなく、直前 2 バイトの分類による効果です。
8. 「a」と「test」のビット単位の確認
以下は統計表そのものの転載ではなく、指定された二つの入力について、実行時に得た符号列を示したものです。
「a」→ 0x4760
本文開始時の状態は 0 です。
対象	UTF-8 バイト値	処理直前の状態	得られた符号
a	97	0	0100011101


本文の符号は 10 ビットです。その後に終端の 1 と、バイト境界までの 0 を 5 個付けます。
部分	ビット列
本文	0100011101
終端	1
埋め草	00000
全体を 8 ビットずつに区切ったもの	01000111　01100000
16 進数	47　60


したがって、結果は 0x4760 です。

復号時は、最後の 5 個の 0 と、その直前の 1 を除くことで、元の 10 ビットだけが残ります。
「test」→ 0x2519d8
対象	UTF-8 バイト値	処理直前の状態	得られた符号
t	116	0	0010010100
e	101	20	0110
s	115	785	0111
t	116	214	01


状態の変化は次のとおりです。
- 最初の t の後は、分類 0 と 20 による状態 20。
- 次の e の後は、分類 20 と 5 による状態 785。
- 次の s の後は、分類 5 と 19 による状態 214。

3. 保存値から重みへの正確な戻し方
保存値を v とすると、実装の計算順序は次のとおりです。
1. 10 億を 10 で割った値、すなわち 1 億の自然対数を求めます。
2. その自然対数に、255 の逆数を掛けます。これを共通の係数とします。
3. v にその係数を掛け、自然指数関数で指数変換します。
4. 得られた値に 10 を掛けます。
5. 最も近い整数へ丸めます。ちょうど二つの整数の中間なら、大きい方へ丸めます。
正の値だけなので、最後の処理は通常の四捨五入に相当します。偶数丸めではありません。

数学的には「10 に、1 億の 255 乗根を v 乗した値を掛けて丸める」と同等ですが、実装は先に根を計算する方式ではなく、上記の自然対数・自然指数関数の順序を使います。

255	1,000,000,000

安定性は独自の並べ替え処理によるものではなく、JavaScript 標準の配列ソートを使うことによります。ECMAScript 2019 以降では、そのソートの安定性が仕様で保証されています。 今回使用した Node.js 22 も該当します。

したがって、新しい親と既存の節点が同じ重みなら、既存の節点が先に残ります。同じ重みの親同士でも、それまでの並び順が維持されます。互換実装では、重みだけでなく、この同順位の扱いも一致させる必要があります。

なお、ハフマン木を作る内部処理そのものは渡された重みの個数に従います。「256 葉」は、正常な統計表から各状態について 256 個の重みを読み込む経路で成立する仕様です。
